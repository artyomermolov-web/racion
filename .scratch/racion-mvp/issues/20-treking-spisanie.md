# 20: Трекинг «съел» + списание кладовки

**What to build:** Пользователь отмечает приёмы как съеденные, удаляет несъеденное и добавляет фактически съеденное из поиска, перегенерирует остаток дня под остаточные цели. Кладовка списывается по факту без двойного вычитания.

**Blocked by:** 19

**Status:** ready-for-agent

Опирается на решения: 07.

- [x] Отметка «съел» / удаление несъеденного / добавление съеденного из поиска.
- [x] Перегенерация остатка дня под остаточные цели.
- [x] Списание кладовки по факту из real-лотов (FIFO по сроку) с guard'ом.
- [x] Тест: повторная отметка/снятие не списывает кладовку дважды.

## Реализация

План не персистится (живёт в состоянии клиента), поэтому «флаг списание применено»
из решения 07 реализован отдельной таблицей `MealWriteOff` по стабильному
клиентскому ключу приёма (`mealKey` = дата|слот|рецепт|порция|номер). Уникальность
`(userId, mealKey)` — это и есть guard от двойного вычитания. Ключ выводится из
содержимого приёма, поэтому переживает перезагрузку (день детерминирован по
userId+дате) и отметки восстанавливаются.

По согласованию с пользователем снятие отметки «съел» ВОЗВРАЩАЕТ списанное в лоты
(сверх решения 07): `MealWriteOffLot` хранит отборы по лотам, возврат добавляет их
обратно (или пересоздаёт лот, если он был удалён вручную).

- Ядро `/core/pantry`: `consumeFromLots` (FIFO по сроку), `writeOffMeal` (guard +
  разворот приёма), `mealDemand`. Тесты — `track.test.ts`.
- Ядро `/core/generator`: `regenerateDayRemainder` (перегенерация несъеденного под
  остаток целей; съеденное вне раскладки — как baseline). Тесты — `generate.test.ts`.
- Слой `/lib/track.ts` + действия `/app/actions/track.ts`; экран — `DayPlan.tsx`.
- Проверено: 235 юнит-тестов, typecheck, прод-билд; сквозной сценарий
  списание→guard→возврат прогнан против БД (FIFO, без двойного вычитания, точный
  возврат).
