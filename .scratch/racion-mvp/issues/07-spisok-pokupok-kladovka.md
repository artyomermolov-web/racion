# 07 — Список покупок пачками + логика кладовки

Type: grilling
Status: resolved
Blocked by: 04
HITL/AFK: HITL

## Question

Как считается список покупок и как он связан с кладовкой? Зафиксировать: агрегацию потребности по диапазону дат и всем людям → вычет кладовки → округление до целых пачек → реальный чек в ₽ и остаток по позиции; живую синхронизацию с планом и правило «вручную изменённые позиции не синкаются до сброса»; чекбоксы «куплено»; подтверждение покупки = снапшот (не пересчитывается при смене цен); перенос купленного в реальные лоты; правило «pending-лоты становятся реальными только после подтверждения»; автосписание на следующий день после запланированного съедения; отсутствие двойного вычитания. Опирается на 04 (модель).

## Answer

**Продуктовые решения (подтверждено):** период списка по умолчанию — неделя от «дня закупки» (даты меняются вручную); списание кладовки в MVP — **по факту «съел»** (авто-списание непомеченного — позже); остатки неполных пачек попадают в кладовку и используются в новых планах.

**Расчёт списка (модуль расчёта, чистый + тестируемый):**
1. **Агрегация потребности** по диапазону дат: для каждого `PlanItem` разворачиваем рецепт → ингредиенты × граммовка × `portion` × `mealType.people`; суммируем по ингредиенту в базовой единице (г/мл/шт).
2. **Вычет кладовки** — вычитаем **только real-лоты** (то, что физически дома). Pending-лоты НЕ вычитаем (это прогноз самой покупки, иначе двойной счёт).
3. **Округление до пачек:** `packsToBuy = ceil((need − realPantry) / packSize)`, не меньше 0. Остаток позиции `= packsToBuy·packSize − (need − realPantry)`.
4. **Чек ₽** = Σ `packsToBuy · pricePerPack`; по каждой позиции показываем «нужно / купить пачек / останется».

**Три состояния запасов (строго раздельно — из разбора piknifood):**
- **real** — дома сейчас; генератор вычитает и приоритетно использует; список вычитает.
- **pending** — прогноз из неподтверждённого списка (то, что вот-вот купим); служит только для превью «что будет дома», генератор НЕ считает своим (нет вычитания → нет фантомов).
- **snapshot** — замороженное состояние списка при подтверждении.

**Живой синк и ручные правки:** пока `confirmedAt` пуст и позиция не `manuallyEdited` — она пересчитывается при изменении плана. Ручная правка ставит `manuallyEdited=true` (позиция замирает) до кнопки **«Сбросить»** (снимает флаг и ре-синкает). Чекбоксы `purchased` по позициям.

**Подтверждение покупки = снапшот:** ставим `confirmedAt`, фиксируем `packsToBuy` и `priceSnapshot`. После этого изменение `pricePerPack` в базе **не меняет** сумму подтверждённого списка. При подтверждении каждая купленная позиция → **real `PantryLot`** (`qty = packsToBuy·packSize`, `expiresAt = дата+shelfLifeDays`, `sourceGroceryListId`); соответствующие pending-лоты промотятся в real.

**Списание по факту (MVP):** отметка `PlanItem.eaten=true` списывает ингредиенты из real-лотов (FIFO по сроку). **Защита от двойного вычитания:** у plan_item флаг «списание применено» — повторная отметка или снятие/возврат не списывают повторно. Авто-списание непомеченного (на след. день после плана) — задел на волну 2, с тем же guard'ом.

**Юнит-тесты (Vitest):**
1. Pending и реальные лоты не смешиваются; pending не вычитается из потребности.
2. Нет двойного вычитания: «съел» списывает один раз; повторная отметка/снятие не меняет запас повторно.
3. Округление до целых пачек и остаток считаются верно (граничные: ровно пачка, чуть больше, кладовка > потребности → 0 пачек).
4. Снапшот: смена цены после подтверждения не меняет сумму подтверждённого списка.
5. Ручная правка замораживает синк до сброса.
6. Подтверждение создаёт real-лоты с верным сроком годности; pending → real.
7. Вычет учитывает число едоков (`people`) и порции.

Опирается на 04 (модель `Ingredient`/`PantryLot`/`GroceryList`/`GroceryItem`).
