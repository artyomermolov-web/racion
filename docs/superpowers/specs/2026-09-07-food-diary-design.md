# Дизайн: Дневник еды + «Что поесть сейчас» для Racion

**Дата:** 2026-09-07
**Под-проект:** A — Дневник еды с движком подсказок «что поесть» (первый шаг объединения «счётчик калорий уровня Yazio + генератор/покупки Racion»)
**Статус:** дизайн на ревью (кода нет)

## Проблема (ради чего всё это)

Реальная боль пользователя (дословно из брейнсторма):

> «Я могу полдня или весь день не есть и в итоге поесть один раз, только потому что не знаю, что поесть / что приготовить, чтобы это было здоровым и вписывалось в КБЖУ. Это целый квест. Именно поэтому я переставал пользоваться Yazio и другими счётчиками: пропустил приём раз, другой — и мотивация пропала. Особенно не нравится сидеть и думать, что съесть, чтобы добрать белок; пока думаешь час-два-три — приём как раз и пропускаешь, и в итоге не добираешь КБЖУ.»

**Вывод.** Классические счётчики (Yazio) показывают дельту («осталось добрать 60 г белка / 500 ккал») и оставляют самое тяжёлое — *решить, что именно съесть* — на пользователя. Это решение-квест и есть триггер отказа от приложения.

Racion может закрыть именно эту дыру, потому что у него **есть генератор**. Поэтому килфича дневника — не «показать дельту», а **дать готовый ответ на дельту**: «вот что съесть прямо сейчас, чтобы добрать белок — здоровое, по остатку КБЖУ, готовится N минут». Ноль раздумий: открыл → увидел → тапнул «съел». Пропущенный приём приложение не осуждает, а пересобирает остаток дня, чтобы всё равно выйти в цель.

## Цель

**Экран дневника внутри того же приложения Racion** (одна кодовая база, один аккаунт, один интерфейс, один движок КБЖУ). Пользователь логирует съеденное — свободно и в один тап из подсказки — и в любой момент получает конкретный ответ «что поесть сейчас», закрывающий остаток КБЖУ.

### Зафиксированные решения (из брейнсторма)

- **Дельта + ответ на дельту.** Показываем остаток до цели (как Yazio) и рядом — кнопку **«Что поесть сейчас»** с конкретными вариантами. Ничего не меняется молча: выбор и тап за пользователем (решение «показывать дельту, без авто-перегенерации» соблюдено).
- **Единицы — граммы/мл + порции/штуки**, под капотом всё в граммах.
- **Охват — текущий день** (остаток дня пересобирается; неделя/покупки пока не трогаются).
- **Архитектура — вариант A:** отдельный чистый модуль `/core/diary`; план/подсказка (предложение) и дневник (факт) — разные сущности, связанные тонким адаптером.

### Опора на существующий код

- `Ingredient` хранит КБЖУ **на 100 г/мл** (`kcalPer100…`), `unit` = `g|ml|pcs`, кастом через `isCustom`+`ownerUserId`.
- `Recipe` имеет `servings`; КБЖУ **считается из состава** (`core/nutrition/recipe.ts`), не хранится.
- Цели — `NutritionProfile` (диапазоны) → `DayTarget` берёт середины (тип уже есть в `core/generator/types.ts`).
- Генератор (`core/generator/generate.ts`, `portions.ts`, `constraints.ts`, `preferences.ts`) уже умеет отбирать/скорить кандидатов и подбирать порцию — движок подсказок переиспользует эти механизмы.
- Общий тип нутриентов — `FoodNutrients` (ккал/Б/Ж/У/клетчатка).
- **Планы не персистятся** — генерируются на лету (отмечено в `core/generator/types.ts`). Дизайн это учитывает.

## 1. Килфича — «Что поесть сейчас» (движок закрытия остатка)

Это центр под-проекта. Всё остальное (лог, дельта) — обвязка вокруг него.

### Что делает

В любой момент дня отвечает на вопрос «что съесть», выдавая **2–3 конкретных варианта**, каждый из которых:
1. закрывает **остаток КБЖУ** (`remaining = DayTarget − съедено`), с приоритетом на **отстающий макрос** (чаще всего белок);
2. проходит жёсткие ограничения (аллергены/блок/keyword-фильтр) и учитывает мягкие предпочтения (избранное/recurring) — переиспользуя `core/generator`;
3. соответствует фильтру усилий: **быстро / готовить / не готовить** (по `timeMin` и требуемой технике) — потому что голодному и уставшему нужен вариант «съесть сейчас», а не готовить 40 минут;
4. логируется **в один тап** («съел») — по построению он здоровый и попадает в остаток.

### Как считает (чистое ядро)

Новый файл `/core/diary/suggest.ts`:

```
suggestNextMeal(input: {
  remaining: FoodNutrients,        // цель − съедено (ккал/Б/Ж/У/клетчатка)
  slot: Slot,                      // следующий незаполненный приём (или "snack")
  candidates: GeneratorRecipe[],   // те же кандидаты, что у генератора
  filters: { maxTimeMin?, mustNotCook?, equipment? },
  constraints: GeneratorConstraints,
  preferences?: Preferences,
  seed: number,
}): SuggestedMeal[]   // топ-3, детерминированно
```

- **Скоринг = закрытие дельты.** Для каждого кандидата подбираем порцию (`bestPortion` уже есть, но по отстающему макросу, а не только по ккал) и считаем, насколько уменьшается взвешенный разрыв. Вес отстающего макроса выше → «добрать белок» реально закрывается. Штраф за перебор ккал.
- **Всегда есть ответ.** Если идеального нет — отдаём лучшие приближения и честно помечаем («добирает белок, но чуть выше по ккал»). Пустой ответ только при пустой базе — тогда явное сообщение.
- **«Пересобрать остаток дня»** — вторичное действие: переиспользует существующий генератор на оставшиеся слоты под `remaining`. Это уже есть по сути; здесь только точка входа «под остаток».

### Почему это ров

Yazio показывает дельту, но не умеет предложить блюдо (нет генератора). Eat This Much умеет план, но не знает твой факт (нет трекинга). Racion соединяет: **факт из дневника → остаток → конкретное блюдо в один тап.** Именно это лечит боль «сижу и думаю что поесть».

## 2. Модель данных и раскладка логики

### Модуль `/core/diary` (чистый, без Prisma/Next — тот же шов тестов)

- `types.ts` — `DiaryEntry`, `DiarySource`, `LoggedAmount`, `DayLog`, `DayProgress`, `SuggestedMeal`.
- `amount.ts` — конверсия **порция/штука ↔ граммы** и КБЖУ порции: `nutrientsForAmount(food, amount)`.
- `aggregate.ts` — суммы по приёмам и за день: `summarize(entries) → totals`.
- `progress.ts` — **остаток до цели**: `remaining(target, totals) → DayProgress` (ккал+Б/Ж/У со знаком; клетчатка — только «добрать»).
- `suggest.ts` — движок «что поесть сейчас» (секция 1).

### Единицы

Каноническая единица — **граммы/мл**. Запись хранит человеческий ввод и грамм-эквивалент:
- продукт (`Ingredient`): `grams` (для `ml` — мл, плотность ~1); КБЖУ = `per100 × grams/100`;
- **штуки** (`unit="pcs"`): `1 шт → gramsPerPiece` (см. ниже) → граммы;
- рецепт (`Recipe`): `servings` (множитель порции); КБЖУ = `КБЖУ порции × servings`;
- быстрые чипсы (½/1/1½, «1 шт», «100 г») — пресеты над теми же полями, не отдельная модель.

### Снапшот КБЖУ в момент лога

Запись хранит посчитанные `nutrients` на момент добавления. Правка еды в базе **не меняет** прошлые записи (принцип неизменяемости из тикета 19).

### Новая Prisma-модель `DiaryEntry` (единственная новая таблица)

```
DiaryEntry
  id              String   @id @default(cuid())
  userId          String
  date            String   // YYYY-MM-DD, локальная дата пользователя
  slot            String   // "breakfast|lunch|dinner|snack"
  source          String   // "ingredient|recipe" (кастом = тот же ref с isCustom)
  refId           String   // Ingredient.id | Recipe.id
  grams           Float?   // source=ingredient (или pcs → граммы)
  servings        Float?   // source=recipe
  kcal protein fat carb fiber  Float   // снапшот
  suggestedRecipeId String? // если пункт пришёл из подсказки/плана — «план vs факт»
  createdAt       DateTime @default(now())
  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
  @@index([userId, date])
```

### Мелкая правка существующей модели

`Ingredient` → добавить `gramsPerPiece Float?` (аддитивная миграция). Нужно, т.к. **штуки теперь первоклассная единица**. Если не задано для продукта — ввод «шт» недоступен, только граммы; сид проставит популярные (яйцо ~55 г и т.п.).

### Связь с генератором/планом — тонкий адаптер, без персистентности плана

Дельта всегда считается из реальных `DiaryEntry` против `DayTarget`. Подсказки строятся на лету из остатка (`suggest.ts`) и/или из сгенерированного дня. Тап «съел» превращает подсказку в реальный `DiaryEntry` с `suggestedRecipeId`. Связки «предложение = факт» в данных нет. Ядро генератора не меняем — переиспользуем.

## 3. Экраны и поток данных

### Навигация

Новая вкладка **«Дневник»** в `src/app/(app)/layout.tsx`. Маршрут — `src/app/(app)/dnevnik/`.

### Экран дня

- Шапка с датой + переключение день назад/вперёд.
- **Сводка сверху:** кольцо «осталось ккал» + бары Б/Ж/У + клетчатка; отстающий макрос подсвечен («не хватает белка»).
- **Главный блок «Что поесть сейчас»** (сразу под сводкой): 2–3 карточки-варианта с КБЖУ и временем; фильтр-чипсы **быстро / готовить / не готовить**; на карточке — «съел» (лог в один тап) и «показать рецепт». Вторичная кнопка «пересобрать остаток дня».
- **Приёмы:** секции завтрак/обед/ужин/перекус — записи (название · количество · ккал) + подытог; тап — правка, свайп — удалить; пустой приём → «+ добавить».

### Поток добавления вручную (шит)

Сегменты **Поиск · Недавнее · Избранное · Своё** → выбор еды → количество (граммы+чипсы / штуки / сервинги) с живым превью КБЖУ → приём (предзаполнен) → «Добавить».
- *Недавнее* — из прошлых `DiaryEntry`; *Избранное* — `FavoriteRecipe` + частые продукты; *Своё* — кастом-еда (тикет 17) в поиске сама.

### Сервер

`src/app/actions/diary.ts`: `addEntry`, `updateEntry`, `deleteEntry`, `logSuggestion`.
Запросы:
- `getDayLog(date) → { entries, progress }` — один индексный запрос + агрегация в ядре;
- `getSuggestions(date, filters) → SuggestedMeal[]` — считает остаток и зовёт `suggest.ts` с кандидатами/ограничениями/предпочтениями пользователя.

Actions делают Prisma-I/O и зовут `/core/diary`; вся арифметика и скоринг — в чистом ядре.

### Главный экран (опционально, минимально)

Строка «залогировано X / цель Y» + «не хватает белка — что поесть?» со ссылкой в дневник.

## 4. Крайние случаи, решения и тесты

### Крайние случаи и решения

- **Штуки без грамм-эквивалента:** если у продукта нет `gramsPerPiece` — «шт» скрыта, доступны граммы.
- **Двойное списание:** `logSuggestion` идемпотентен по `(date, slot, suggestedRecipeId)`; удаление возвращает подсказку. (Тест: повтор не дублирует.)
- **Дата/таймзона:** `date` — локальная календарная дата (строка `YYYY-MM-DD`) с клиента; граница «сегодня» — локальная полночь, без UTC-дрейфа.
- **Перебор:** дельта в минус показывается честно («+120 ккал сверх цели»), не обрезается. Клетчатка — только «добрать».
- **Поздний старт дня / пропуски:** если приёмы пропущены, `suggest.ts` считает от остатка на текущий момент (не «размазывает вину»); можно предложить закрыть остаток за 1–2 приёма.
- **Нет идеального варианта:** отдаём лучшие приближения с честной пометкой; пусто — только при пустой базе.
- **Правка/снапшот:** правка количества пересчитывает снапшот из текущих данных; прошлые дни неизменны.
- **Пустые состояния:** нет нормы → «заполни профиль»; ничего не залогировано → empty + «что поесть сейчас».
- **Офлайн (PWA):** вне под-проекта; записи серверные (задел на тикет 21).

### Тестовые швы (Vitest)

- **Чистое ядро без БД (главная поверхность):**
  - `suggest.ts` — **ранжирование закрывает отстающий макрос** (при дефиците белка топ-вариант добирает белок); уважает ограничения/фильтр времени; детерминизм по seed; всегда ≥1 вариант при непустой базе.
  - `amount.ts` — граммы↔сервинги↔штуки.
  - `aggregate.ts` — суммы по приёму/дню.
  - `progress.ts` — дельта (минус/перебор, клетчатка min-only).
- **Неизменяемость снапшота:** правка исходной еды не меняет существующую запись.
- **Action-уровень:** add/update/delete/logSuggestion + гард двойного списания.
